# Survey of LLM-based C-to-Rust systems: rule, search and per-cell evidence

This document is the evidence behind the survey table in the paper (Section II, Table I). The same data is in machine-readable form in [`survey-evidence.json`](survey-evidence.json); the two files are generated from one source and agree cell for cell.

For each system we record two properties of its own evaluation:

- **Held-out.** Its evaluation uses inputs disjoint from those that drove its repair loop.
- **Mut.** It mutation-tests its oracle: it injects known-wrong translations into its check and reports whether the check rejects them.

A cell records what the paper documents. It is not a claim about what the authors did but did not write down.

## 1. Inclusion rule

A paper is included when all five criteria hold. Each criterion is recorded per paper with a quote in the JSON file.

- **I1.** Translates C source code into Rust (C may be one of several source languages).
- **I2.** An LLM generates or repairs the Rust (alone or with program analysis or a rule-based translator).
- **I3.** The paper presents a translation pipeline that produces complete Rust for C functions, files or programs (not a benchmark, user study, empirical study of other tools, survey, single-construct tool, or optimizer of already-translated Rust).
- **I4.** The paper reports, for translations it produced, a success rate from an automated correctness or equivalence check (tests, differential testing or fuzzing, symbolic execution, verification). Compile rate, unsafe ratio, similarity or LLM-judge metrics alone do not count.
- **I5.** First public version (arXiv v1, or venue publication if not on arXiv) on or before 2026-10-31.

The rule, not artifact availability, decides membership. It admits systems whose artifacts we cannot run, and it excludes benchmark papers (CRUST-Bench, C2Rust-Bench, RustRepoTrans, TRACTOR) because they contribute no translation system.

## 3. Coding rules

We code every included paper the same way, from its latest version (the version read is listed per system).

1. **Loop.** Every pipeline step in which running the program on inputs (tests, fuzzing, differential or equivalence tests, symbolic execution, verification) decides whether a candidate is repaired, regenerated, selected or accepted. Compiler-only feedback is not an input-driven loop.
2. **Evaluation check.** The check whose pass rate the paper reports as correctness.
3. **Held-out**, decided in this order:
   1. n/l if there is no input-driven loop.
   2. Yes if at least one reported correctness result uses inputs the paper states were unavailable to the loop (quotable).
   3. n/a if the evaluation check is symbolic or exhaustive only.
   4. No otherwise.
   `n/l` means the evaluation inputs are held out by construction, because no input-driven loop exists. `n/a` means a symbolic check, which has no sampled input set to hold out. When a paper reports both a sampled and a symbolic tier, the sampled tier decides and the symbolic tier is footnoted.
4. **Mut.** Yes only if the paper injects known-wrong translations (mutants, seeded bugs, deliberately wrong translations) into its acceptance or evaluation check and reports whether the check rejects them. Recall checks against an independent oracle, coverage, and manual review are noted but coded No.
5. **Evidence.** Each cell carries a verbatim quote of at most 15 words with section and PDF page, or the list of terms searched when the answer is an absence. We searched at least: held-out, hold out, holdout, disjoint, unseen, hidden, separate, never exposed, never seen, validation test, split, overfit, leak, mutant, mutation, inject, seeded, fault, known-wrong, incorrect translation, false negative, false positive, soundness, oracle, adequacy, coverage, kill. Every quote was checked by script against the PDF text, except those from papers whose full text was read as HTML (Tymcrat) or not at all (C2RustTV, abstract only).

## 6. Per-system evidence

### VERT

*VERT: Verified Equivalent Rust Transpilation with Large Language Models as Few-Shot Learners*. Aidan Z. H. Yang, Yoshiki Takashima, Brandon Paulsen, Josiah Dodds, Daniel Kroening. arXiv 2404.18852; version read: v2 (25 May 2024); first public 2024-04-29; venue: ASE 2025 (as 'VERT: Polyglot Verified Equivalent Rust Transpilation with Large Language Models', DOI 10.1109/ASE63991.2025.00123).

- **Loop:** Candidate is checked against the rWasm oracle by bolero PBT, then bounded and full Kani; on failure the LLM is re-prompted (up to 20 times). "if verification fails, we regenerate a new candidate transpilation until verification succeeds" (Abstract, p.1)
- **Evaluation check:** The same tiers: PBT pass (sampled), bounded Kani and full Kani (symbolic). "For PBT, no counterexamples within 120 seconds counts as success." (Sec. 5, p.15)
- **Held-out: No‡.** "if verification fails, we regenerate a new candidate transpilation until verification succeeds" (Abstract, p.1). Sampled tier (bolero PBT) is the loop's own check. Bounded and full Kani tiers are symbolic (n/a).
- **Mut.: No.** Absence: searched the term list above. 'Mutation Guided Entry Point Identification' (Sec. 4, p.9) mutates constants in the rWasm oracle to locate a function's arguments for the harness; it does not feed wrong translations to the check.
- **Artifact (R = Meets):** https://zenodo.org/records/10927704 ; https://github.com/YoshikiTakashima/vert. Paper p.23: 'the LLM Rust transpilations is available at https://zenodo.org/records/10927704'. Re-graded in this study (systems/vert/).

### FLOURINE

*Towards Translating Real-World Code with LLMs: A Study of Translating to Rust*. Hasan Ferit Eniser, Hanliang Zhang, Cristina David, Meng Wang, Maria Christakis, Brandon Paulsen, Joey Dodds, Daniel Kroening. arXiv 2405.11514; version read: v3 (17 Apr 2025); first public 2024-05-19; venue: none found.

The paper spells the tool 'Fluorine' (20 times, never 'Flourine'); its artifact uses 'flourine', and our paper writes FLOURINE.

- **Loop:** Cross-language differential fuzzer; counterexamples drive one of four feedback strategies until the fuzzer finds none or the budget is spent. "fuzzer fails to find a counterexample after a configured timeout, the translation is considered validated" (Sec. 1, p.2)
- **Evaluation check:** Success = the same fuzzer finds no counterexample. "checked for correctness by the fuzzer, and fixed if needed by applying feedback strategies" (Sec. 6, p.7)
- **Held-out: No.** "checked for correctness by the fuzzer, and fixed if needed by applying feedback strategies" (Sec. 6, p.7). Evaluation check is the loop's own fuzzer.
- **Mut.: No.** Absence: searched the term list above. Only line coverage: 'our fuzzer achieves an average line coverage of 97%' (Sec. 4, p.6). Coverage is not mutation testing.
- **Artifact (R = Meets):** https://d34gtk3knhjgeg.cloudfront.net/artifact.tar.gz. Abstract p.1 link; tarball ships C/Go functions with labelled LLM Rust translations. Re-graded in this study (systems/flourine/).

### SpecTra

*SpecTra: Enhancing the Code Translation Ability of Language Models by Generating Multi-Modal Specifications*. Vikram Nitin, Rahul Krishna, Baishakhi Ray. arXiv 2405.18574; version read: v3; first public 2024-05-28; venue: none found.

- **Loop:** Two input-driven steps. (1) Spec self-consistency filter: LLM regenerates the C program from each candidate static spec / description, and the regenerated C is run on the existing (CodeNet) test input/output pairs; failing specs are discarded; I/O specs are validated by running the original C. (2) Spec-guided translation is a fall-through: translate with the static spec, and if that translation is not correct, retry with the I/O spec, then the description, then no spec; pass@k = any of the first k candidates passes the ground-truth test. Case study: up to 3 rounds of compiler-feedback repair; I/O specs come from instrumenting the provided end-to-end tests. "If this approach fails, we then use the input-output specifications" (Sec. 3.3, p.5 (v3); self-consistency filter Sec. 3.2, p.5; Fig. 1 'Correct?' gate)
- **Evaluation check:** Compile the Rust translation, run it on the CodeNet ground-truth test input, compare stdout to the expected output; pass@1/2/3 out of 300 C-to-Rust programs. Case study: GNU cat end-to-end tests with FFI-linked mixed C/Rust build. "If the output matches the ground truth test output, then we mark" (Sec. 4.3, p.6 (v3))
- **Held-out: No.** "we used existing test input and expected output pairs" (Sec. 3.2, p.5 (v3) (these pairs are the evaluators of the self-consistency filter)). The same provided ground-truth tests (CodeNet input/output; repo ships one input.txt/output.txt per problem) both filter specifications and decide whether the pipeline falls through to the next spec, and pass@k credits any of k candidates that passes them. In the cat case study, the I/O specs are collected by running 'the provided end-to-end tests', which are also the evaluation tests (Sec. 6.1-6.2, p.10).
- **Mut.: No.** Absence: searched the term list above. Only gcov coverage of LLM-generated tests (91.5% average, Sec. 5 RQ4, p.8) and manual inspection of some specs; neither is an oracle mutation test. EvalPlus mutation is mentioned only in related work.
- **Artifact (R = No):** https://github.com/spectra822/icse26. Branch main1: spectra/data/Project_CodeNet_mini/data/p*/C/*.c (300 C files), derived/input_output/data/p*/input.txt+output.txt (tests), c_spec_store/ (generated specs), translate.py/evaluate.py. Zero .rs files in the tree; README tells users to regenerate translations with an LLM into ../results_store, which is not committed. The cat case-study code and outputs are not in the repo. gh search repos for SpecTra found no other repo.

### SmartC2Rust

*SmartC2Rust: Iterative, Feedback-Driven C-to-Rust Translation via Large Language Models for Safety and Equivalence*. Momoko Shiraishi, Yinzhi Cao, Takahiro Shinagawa. arXiv 2409.10506; version read: v3; first public 2024-09-16; venue: ICSE 2026.

- **Loop:** Algorithm 1 stage (iii): per-unit compile-repair loop, then a semantic repair loop that runs the test cases on C and Rust, compares outputs and execution flow (call stacks, inputs, return values), and re-prompts the LLM until compile, runtime and semantic errors are gone (bounded by REPAIR_MAX). Tests come from the program's repo (built-in), third parties (provided) or were hand-written by the authors (created); C golden outputs are recorded in advance by a shell script.
